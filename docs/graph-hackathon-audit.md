# Graph Hacks: official-resource findings

Research date: 18 October 2026. Scope: the public organizer resources, challenge overview, rules, organizer tutorial, and first-party product documentation. No project implementation was inspected. Incident-response applications below are interpretations of the documented capabilities, not claims about this repository or extra competition requirements.

## Executive findings

- **The current competition has three tracks, not two.** The two compared in depth here are Track 01, **Agents That Act on Connected Data**, and Track 02, **Agent Memory and Coordination**. Track 03 is **Company Brain**. Both the overview and rules explicitly allow entering any or all tracks. [Overview](https://www.wemakedevs.org/hackathons/falkordb#tracks), [rules, rule 5](https://www.wemakedevs.org/hackathons/falkordb/rules).
- **FalkorDB must be the primary graph database and central to product behavior.** A visualization over ordinary storage does not qualify. Rule 3's practical test is whether the product still works when FalkorDB is removed. [Rules, 2–3](https://www.wemakedevs.org/hackathons/falkordb/rules).
- **MCP, GraphRAG SDK, Graphiti, Cognee, LangChain, LlamaIndex, QueryWeaver, and every named algorithm are not individually mandated.** The track bullets are labeled “Key focus”; the stack names appear as integration options. The rules permit any language/framework and require submission of the **Cypher queries or graph algorithms** the product depends on, not every algorithm or both categories. [Overview](https://www.wemakedevs.org/hackathons/falkordb), [rules, 4 and 10](https://www.wemakedevs.org/hackathons/falkordb/rules).
- The organizer's linked tutorial already describes **Blast Radius**, a bounded on-call incident agent with dependency traversal, ownership/on-call lookup, recent changes, shortest paths, PageRank, graph-backed findings, and fixed MCP tools. This is directly relevant first-party design guidance; reproducing its feature list alone does not establish original hackathon contribution. The rules judge original event work. [Organizer tutorial](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph), [rules, 8–9](https://www.wemakedevs.org/hackathons/falkordb/rules).

## Mandatory rules versus guidance

### Explicit rules and submission obligations

The [rules page](https://www.wemakedevs.org/hackathons/falkordb/rules) establishes:

1. Solo or teams of at most four; each participant belongs to only one team (rule 1).
2. FalkorDB is the primary graph database, supports central functionality, and does real work rather than decorate another storage system (rules 2–3).
3. Docker, self-hosted FalkorDB, and FalkorDB Cloud are accepted. Language, framework, frontend, and deployment platform are unrestricted (rule 4).
4. Declare **every** entered track; any or all of the three are allowed (rule 5).
5. Use permitted public, synthetic, or own data. The same rule explicitly prohibits loading private, login-protected, paywalled, personal, or otherwise restricted information. “Own data” should not be read as overriding those exclusions; synthetic operational records are a straightforward fit for an incident demo (rule 6; last clause is interpretation).
6. Event window: October 15, 12:01 AM IST through October 18, 11:59 PM IST; submission closes at the end. Main coding and design begin after the start; prior ideas, notes, model sketches, and diagrams are allowed. Reusable frameworks, libraries, public APIs, templates, tools, and public datasets/assets are allowed; original event work is judged (rules 7–9). The overview identifies the year as 2026.
7. Submission includes a public source repository; README with setup instructions **and graph data model**; dependent Cypher queries **or** graph algorithms; working demo video; live deployment **or complete local setup instructions if it cannot be deployed**; and entered track(s) (rules 5 and 10). A live deployment is preferred, not an unconditional requirement; the overview FAQ agrees.
8. Disclose AI coding-assistant use. Participants must understand and explain the code, graph model, queries, architecture, and technical decisions. Entirely generated projects without meaningful contribution, verification, or understanding may be rejected (rules 11–13).
9. Participant/team ownership of developed IP, respectful conduct, and compliance with the organizer's [Code of Conduct](https://www.wemakedevs.org/coc) apply. Harassment, discrimination, plagiarism, and judging manipulation can disqualify (rules 15–18). The rules state that pre-event updates may be announced through community channels.

### Challenge expectations and non-mandatory focus areas

The [challenge](https://www.wemakedevs.org/hackathons/falkordb#challenge) asks for a working agent or group with FalkorDB as the context layer, graph-shaped decisions/actions, learning remembered, and traceable answers. It lists following connections, cross-session memory, shared agent state, connected organizational knowledge, and answer paths as work for the graph.

Those broad expectations matter for alignment, but the rules allow one agent and one track. It would overstate the text to turn every cross-track bullet into a universal pass/fail requirement. In particular, the public pages do not specify a minimum agent count, hop count, algorithm count, throughput target, tenant count, or scoring weights. MCP is an explicit Track 01 focus, so it is relevant evidence of alignment; it is not separately declared mandatory technology. [Overview and FAQ](https://www.wemakedevs.org/hackathons/falkordb), [rules](https://www.wemakedevs.org/hackathons/falkordb/rules).

## What the graph resources actually add

### Cypher, multi-hop traversal, and bounded tools

FalkorDB supports a subset of OpenCypher with proprietary extensions. `MATCH` supports chained multi-hop patterns, directed/undirected relationships, variable-length paths `[:TYPE*minHops..maxHops]`, and named paths that can return nodes/relationships. Omitted bounds default to 1 and infinity. Client parameter APIs allow values to be supplied separately. [Cypher](https://docs.falkordb.com/cypher/), [MATCH](https://docs.falkordb.com/cypher/match), [coverage](https://docs.falkordb.com/cypher/cypher-support).

**Incident-response value:** a dependency relation can answer “what depends on this failed service?” across several hops and return its evidence route. Direction is substantive: if A depends on B, finding B's impact walks toward B from its dependents. Ownership, on-call, changes, and findings can be connected to the same services. The organizer specifically demonstrates a fixed tool catalog with authored queries, validated service names, depth/time/result bounds, and read-only investigation queries. It distinguishes “unknown service,” “no connection recorded,” “answered with path,” and “answered from memory.” This is official example guidance, not a requirement to use that exact schema or six tools. [Organizer tutorial](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph).

**Important limits:** `LIMIT` does not cap preceding eager writes/aggregations. An unreferenced relationship may only establish existence rather than count all parallel edges; edge aliases must be referenced when every relationship matters. Indexes do not optimize `<>` filters. Thus result limits alone do not establish bounded work, and parallel dependency edges need deliberate handling. [Known limitations](https://docs.falkordb.com/cypher/known-limitations). A path is evidence of stored connectivity, not proof of real-world causality or completeness (interpretation, consistent with the tutorial's empty-result distinction).

### Graph algorithms

The [algorithm catalog](https://docs.falkordb.com/algorithms/) lists BFS, SPpaths, A*, SSpaths, minimum spanning forest, PageRank, betweenness/harmonic centrality, WCC, CDLP, and maximum flow. These are options to select by the question being answered.

- **BFS:** explores outward by depth and returns visited nodes/edges. Its documented signature is `algo.bfs(start_node, max_depth, relationship)`; relationship filtering and depth limits constrain exploration. Useful for a bounded neighborhood, but a BFS visited list is not a separate evidence path for every result. High connectivity/depth increases memory/work. [BFS](https://docs.falkordb.com/algorithms/bfs).
- **SPpaths:** point-to-point weighted routes with `relTypes`, `relDirection`, `maxLen`, `maxCost`, and `pathCount`; returns path, weight, and cost. Useful for “why are these services connected?” with an explicit search budget. `weightProp` is minimized; `costProp` is a separate constraint. Neither is automatically an incident risk score. [SPpaths](https://docs.falkordb.com/algorithms/sppath).
- **PageRank, betweenness and harmonic centrality:** topology-based ranking can prioritize structurally important services or connectors. PageRank is demonstrated in the organizer's “load-bearing” tool; a topological score alone does not establish fault causality or business severity. [Catalog](https://docs.falkordb.com/algorithms/), [tutorial](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph).
- **WCC/CDLP:** components and communities can expose disconnected islands or clusters. WCC ignores direction, so it cannot substitute for directed blast-radius analysis. **SSpaths** broadens exploration from one source. **A*** is documented with a geographic heuristic; **MSF/max flow** address spanning/capacity questions and only add value if the incident model actually has those semantics. [Catalog](https://docs.falkordb.com/algorithms/).

Applications in this list are interpretations. The catalog's summary/FAQ wording is inconsistent about some path procedures; use each specific procedure's documentation for its parameters rather than assuming one common algorithm signature.

### Official clients, setup, and operational memory

The official clients are Python `falkordb-py`, Node.js `falkordb-ts`, Java `jfalkordb`, Rust `falkordb-rs`, Go `falkordb-go`, PHP `falkordb-php`, and C# `NFalkorDB`. The client directory separately labels additional clients, including legacy RedisGraph clients, as not officially tested/supported. The direct client adds database connectivity and result decoding without requiring a retrieval framework; the organizer's incident example explicitly uses the raw Python client. [Client directory](https://docs.falkordb.com/getting-started/clients), [tutorial](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph).

Docker/Cloud supply the running database; Browser supplies inspection and visualization. The documentation index links durable storage guidance covering RDB/AOF and Docker volumes. Cross-session graph memory and durability across container replacement are separate properties; selecting a graph name alone is not a storage-persistence configuration. [Operations/documentation index](https://docs.falkordb.com/_llms/falkor-db/documentation.txt), [Graphiti MCP persistence guidance](https://docs.falkordb.com/agentic-memory/graphiti-mcp-server).

For Track 02's concurrency focus, the core docs describe parallel reads and **serialized writes per graph**. Do not equate “high-concurrency reads/writes” with unlimited simultaneous write execution, or infer application-level handoff correctness from storage concurrency alone. [Concurrency](https://docs.falkordb.com/design/concurrency).

### MCP: protocol versus specific servers

The official FalkorDB MCP server exposes graph querying, read-only support, graph listing, node/relationship management, and graph deletion. Its role is interoperable tool access for MCP clients. That generic database tool surface is different from the organizer tutorial's domain-specific, bounded `blast_radius`, `who_to_wake`, `recent_changes`, `path_between`, `load_bearing`, and `recall` tools. MCP by itself does not enforce those domain bounds or choose sound incident actions. [FalkorDB MCP docs](https://docs.falkordb.com/genai-tools/mcpserver/), [official server repository](https://github.com/FalkorDB/FalkorDB-MCPServer), [tutorial](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph).

**Graphiti MCP is a different server:** it adds episode ingestion/retrieval, fact/node search, groups, and memory management over Graphiti. It is useful if multiple compatible clients need the same episodic memory. Its docs describe queued/asynchronous episode processing, so submission/acceptance of an episode should not be assumed to mean immediately completed extraction. [Graphiti MCP](https://docs.falkordb.com/agentic-memory/graphiti-mcp-server).

## Source conflicts and unresolved requirements

1. **Track count and multi-track entry:** current overview/rules clearly say three tracks and allow any/all. The linked organizer tutorial says “You enter one track,” which conflicts with those pages. Treat the explicit rules and FAQ as authoritative for submission, not that tutorial sentence. [Rules](https://www.wemakedevs.org/hackathons/falkordb/rules), [overview](https://www.wemakedevs.org/hackathons/falkordb), [tutorial](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph).
2. **Judging thresholds:** no numerical rubric, required benchmark, algorithm count, or minimum autonomous-action scope was found in the fetched challenge/rules/resources. The organizer tutorial describes persuasive demonstrations, not a published weighted scoring system. Whether an investigation-only action meets a particular judge's expectations is not defined precisely in those pages.
3. **Product docs are living and internally inconsistent:** the Cypher coverage page lists UDFs as unsupported in its body but supported in its FAQ. Documentation boilerplate emphasizes Redis protocol, while the integration hub documents experimental Bolt. Avoid blanket Neo4j compatibility or blanket “no Bolt” assertions; check the target release and specific client/procedure. [Coverage](https://docs.falkordb.com/cypher/cypher-support), [integrations](https://docs.falkordb.com/integration/), [clients](https://docs.falkordb.com/getting-started/clients).
4. **Graphiti links/API drift:** the sponsor's linked `graph-db-configuration#falkordb` URL returned a Page Not Found response. The replacement owner page uses `Graphiti(graph_driver=FalkorDriver(...))`, whereas the sponsor guide demonstrates a `falkor://` constructor. This research establishes the integration, not interchangeability of those APIs. [Owner configuration](https://help.getzep.com/graphiti/configuration/falkordb-configuration.md), [sponsor guide](https://docs.falkordb.com/agentic-memory/graphiti).
5. **Isolation and memory semantics:** graph scoping is a useful separation primitive, but it does not itself authenticate who may select a graph, define fact freshness/conflict resolution, or orchestrate a handoff. These are design implications rather than extra rules. GraphRAG's own grounding docs explicitly leave filtering/abstention enforcement to the application. [Grounding](https://docs.falkordb.com/graphrag/reliability-and-grounding).
6. **Evidence boundary:** public pages were fetched on the research date; no registration-only submission fields, Discord announcements, runtime examples, video transcripts, or local project behavior were verified. Framework examples and benchmark claims should not be treated as proof of this project's correctness or incident-response accuracy.

## Project implementation audit

### Verdict

**AFTERSHOCK demonstrates the core graph-driven workflow in a bounded synthetic sandbox. It has not implemented every Track 01/02 focus item, nor is this checkout a completed submission.** The public workflow consists of two deterministic workers; it is not the model-selected MCP agent demonstrated in the organizer tutorial. The brief/rules do not explicitly mandate a chat UI or LLM, but the tutorial's model-driven tool selection is a material difference and must not be claimed as implemented in the public flow.

The distinction is between (a) a working graph-centered implementation, (b) coverage of every focus area, and (c) completed submission deliverables. Only (a), within the stated scope, is demonstrated here. There is no published numerical rubric from which to calculate a meaningful “percentage complete.”

### Using the official resources: graph-first priorities

These are recommendations, not source changes made during this audit.

1. **Put exact paths at the center of the demonstration.** The organizer tutorial's strongest proof is depth one versus deeper traversal, with each returned path next to its result. Our query already returns `path`; make selected paths explicit and consider a validated depth control. With this fixture, depth one reaches `orders`; depth three can also reach `storefront`, `acme`, and `orbit`. This is more directly tied to the graph brief than additional conversational UI. [Tutorial](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph), [MATCH docs](https://docs.falkordb.com/cypher/match).
2. **Fix memory selection before claiming stronger learning.** Distinguish historical incidents, operator notes, and verified sandbox receipts. Retrieve relevant history first and a small, separate recent-note allowance; retain dates and scope. Repeated notes for one demonstration are not independent learned lessons. Graphiti is useful if temporal knowledge extraction becomes a requirement, but typed nodes and authored retrieval are sufficient for the current scope. [Tutorial memory section](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph#problem-4-memory-the-agent-can-find-next-session), [Graphiti docs](https://docs.falkordb.com/agentic-memory/graphiti).
3. **Use database-enforced read-only calls for observation.** Current `query()` uses the client's general `graph.query()` for reads and writes alike. The authored tool queries are read-only, but the official tutorial recommends the read-only API for observation. Split observation from deliberate mutations without exposing arbitrary generated Cypher. [Tutorial](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph), [`graph.ts`](../src/lib/graph.ts).
4. **If adding one algorithm, choose a real route question.** A bounded shortest-path tool answering “which recorded route connects this customer/service to checkout?” has a clear incident purpose. `algo.SPpaths` can return the actual path and cost. Define edge weights if weighted routes are used. PageRank is appropriate only if structural criticality/ranking becomes a real product question; it is not automatically incident severity. [SPpaths](https://docs.falkordb.com/algorithms/sppath), [algorithm catalog](https://docs.falkordb.com/algorithms/).
5. **MCP is a focused optional extension if covering that bullet matters.** Wrap the existing bounded, validated tools for compatible agent clients. Do not count normal function calls as MCP or expose the official generic server's full write/delete surface by accident. Adding MCP does not itself improve the correctness of a traversal or decision. [Official MCP docs](https://docs.falkordb.com/genai-tools/mcpserver/), [tutorial tools](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph#problem-2-the-agent-should-not-write-the-cypher).
6. **Do not add GraphRAG just to use a named resource.** The organizer itself uses the raw client for its structured graph example. Our current data is explicitly modeled. GraphRAG SDK earns its place when ingestion of runbooks/postmortems/documents becomes part of the product, with source provenance and extraction evaluation. [Tutorial architecture rationale](https://www.wemakedevs.org/blogs/how-to-build-an-agent-that-reasons-over-a-graph#what-each-piece-is-doing), [GraphRAG SDK](https://github.com/FalkorDB/GraphRAG-SDK).

### Important positioning and scope limits

- The linked official tutorial already uses an incident blast-radius problem. Our differentiated demonstration should emphasize constraint-driven proposal revision, evidence-gated refusal, persisted cross-process handoff, atomic/idempotent sandbox execution, and independent verification—not imply that incident dependency traversal itself is a unique idea.
- Public `/api/investigate` and the responder pass `toolSelection: "fixed"`. The optional internal model loop in `agent.ts` does not make the demonstrated workflow a model-planned MCP agent. A chat box is not required to add model-selected tools, but none should be claimed unless actually wired and verified.
- The implementation is explicitly scoped to `deploy-247`, `checkout`, `payments`, `fast_payments`, and rollback target `v2.4.6`. These literal guards are sensible for sandbox correctness but mean this is not yet a general incident platform. See [`decision.ts`](../src/lib/decision.ts).
- Audit/handoff/receipt snapshots contain JSON payloads alongside graph links. Those are legitimate audit snapshots, but not every payload field or agent identity check is currently traversed as a graph relationship. The strongest graph work is in domain traversal, constraints/runbooks, targets, and execution provenance.
- Full graph durability uses AOF and a Docker volume; graph naming alone is not sufficient. There is no external production integration. The sandbox HTTP probe is a deterministic replay of a synthetic request against persisted configuration.
